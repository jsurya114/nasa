**What and why.** Sections 3, 5 and 10 of `docs/MOBILE_APP_DESIGN.md`: the page half of push. Everything is inert in a normal browser and in an app build that has no push support.
- **Asking, in context.** After sign-in (`PushSetup`, inside the driver and admin route guards, so never before sign-in) the page asks the shell about push. If the phone cannot get a token (a simulator, or no Expo project yet) nothing happens. If notifications are already allowed, the phone is registered quietly. If the answer is still open, our own short explanation appears first ("Turn on notifications?", English and Spanish); only **Turn on** shows the system prompt. **Not now** asks nothing further for 7 days. If the person refuses, nothing is registered and the app works as before.
- **Registering.** The token comes from the shell (`push.getToken`); the page sends it with the platform and shell version to `POST /<area>/push-token`, with the person's own access token, so the server takes the person from the token. The request uses a plain client with no interceptors, so a failure (including a `401`) can never trigger a refresh or a sign-out, and it is silent: the next start tries again.
- **Signing out.** `sessionStore` gained `onSignOut(hook)`. At the start of an in-app sign-out the hook receives the area and the access token the page still holds, and `PushSetup` sends `POST /<area>/push-token/remove` with it. It is not waited for and its failure is ignored, so signing out is never delayed or blocked; a sign-out of the other area removes nothing.
- **Ordering (review fix, 2 Nov 2026).** The first version let a registration that was still on its way when the person signed out arrive after the removal, which put the phone back on a signed-out account; it could equally have taken the phone from the next person to sign in. Registering and removing for one area are now sent one at a time in the order they started (`inOrder` in `push.js`), so a removal always lands behind a registration already in flight. A registration also notes the sign-in it belongs to (`sessionGeneration(area)`, which changes on every sign-in and sign-out) and is dropped before it is sent if that has changed while it waited for the phone. The local sign-out is still immediate and never waits for either. **Known limit (raised by the automated security review of this change):** this ordering is kept by the page only. A registration that the page gives up on (the 5-second timeout) may still be delivered to the server later than the removal sent behind it, and the removal cannot undo something that has not arrived yet. The exposure is the same small one as the expired-session case below (generic lock-screen text, a tap still checks sign-in, and the next sign-in on the phone moves the token to its new owner). A full fix belongs on the server: refuse or ignore a registration whose access token was issued before the person's latest removal for that token (or record a per-token removal time and compare), which is a backend change to `deviceTokenQueries.register` and the controllers and is proposed as a follow-up for Jayasoorya, not made here. This covers the normal logout and the other in-app sign-out paths. When the session is already dead (an expired refresh token), the removal cannot be authorised and the phone stays registered to that person until the same phone is used to sign in (the server then moves it to the new person) or Expo reports the token invalid. Lock-screen text is generic and a tap checks sign-in, so the exposure is small.
- **Tap routing (`PushTapRouter`).** On the shell's data-free nudge (and once at start, for a tap that opened the app from closed) the page collects the screen name through the bridge and maps it per area: driver `availability`, `deliveries`, `agreement`; admin `access-codes`. A name not listed for the signed-in area, or any URL, is ignored. If nobody is signed in yet the tap waits up to 10 minutes for a sign-in. If someone is signed in whose area cannot open it, it is dropped and does not follow a later sign-in. The route guards (agreement, role, sign-in) and the server still decide what is shown.

New tests use the real components with the fake shell and fake server: nothing happens in a browser, without the capability, on a phone that cannot get a token, or with no session; quiet registration for the right area with the person's token and the right body; a failed or `401` registration is silent and triggers no refresh or sign-out; the explanation comes first and the system prompt only after "Turn on"; "Not now" asks nothing and is not repeated within a week (and is again after one); a system "no" registers nothing; sign-out sends the removal with the token the page held, for the right area, without waiting for it (a removal that never answers does not block the sign-out); another area's sign-out removes nothing; a browser sign-out sends nothing; tap routing for each screen name, a cold-start tap, a wait for sign-in, expiry after ten minutes, a screen the area cannot open, hostile names (`https://...`, `/admin/dashboard`, `__proto__` and others), non-tap events, and no calls without the capability.

**Android first run (review fix).** Android's notification module reports `denied` with `canAskAgain: true` before the first grant; it has no "not asked yet" state like iOS. `PushSetup` only offered the explanation for `undetermined`, so Android never saw it. It now asks for `undetermined` and for `denied` while `canAskAgain` is true, and leaves a refusal the system will not repeat alone.

**Risks and follow-ups.** There is no "notifications are off, open settings" screen yet (the shell action `push.openSettings` exists); a person who refused must find the phone's settings themselves. Account-level on/off switches per event are left for later. The design's note on logout cleanup is met on the normal path only, as described above.
- Review-fix tests: Android's first-run shape (`denied`, `canAskAgain: true`) shows the explanation, Turn on registers, and Not now is remembered; a registration held at the server while the person signs out is followed by the removal (order register, remove; the phone ends unregistered; the removal is not sent until the registration answers; the sign-out itself is not delayed); a registration still waiting on the phone when the person signs out and the next person signs in is dropped and never replaces the next person's registration. Mutation checks: running registrations and removals without ordering, removing the sign-in check, and asking for `undetermined` only each fail exactly their tests.
