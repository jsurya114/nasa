**What and why.** Sections 3, 5 and 10 of `docs/MOBILE_APP_DESIGN.md`: the page half of push. Everything is inert in a normal browser and in an app build that has no push support.
- **Asking, in context.** After sign-in (`PushSetup`, inside the driver and admin route guards, so never before sign-in) the page asks the shell about push. If the phone cannot get a token (a simulator, or no Expo project yet) nothing happens. If notifications are already allowed, the phone is registered quietly. If the answer is still open, our own short explanation appears first ("Turn on notifications?", English and Spanish); only **Turn on** shows the system prompt. **Not now** asks nothing further for 7 days. If the person refuses, nothing is registered and the app works as before.
- **Registering.** The token comes from the shell (`push.getToken`); the page sends it with the platform and shell version to `POST /<area>/push-token`, with the person's own access token, so the server takes the person from the token. The request uses a plain client with no interceptors, so a failure (including a `401`) can never trigger a refresh or a sign-out, and it is silent: the next start tries again.
- **Signing out.** `sessionStore` gained `onSignOut(hook)`. At the start of an in-app sign-out the hook receives the area and the access token the page still holds, and `PushSetup` sends `POST /<area>/push-token/remove` with it. It is not waited for and its failure is ignored, so signing out is never delayed or blocked; a sign-out of the other area removes nothing.
- **Ordering (review fix, 2 Nov 2026).** The first version let a registration that was still on its way when the person signed out arrive after the removal, which put the phone back on a signed-out account; it could equally have taken the phone from the next person to sign in. Registering and removing for one area are now sent one at a time in the order they started (`inOrder` in `push.js`), so a removal always lands behind a registration already in flight. A registration also notes the sign-in it belongs to (`sessionGeneration(area)`, which changes on every sign-in and sign-out) and is dropped before it is sent if that has changed while it waited for the phone. The local sign-out is still immediate and never waits for either. **The server enforces the ordering too (review fix, 2 Nov 2026).** The page's ordering cannot stop a registration that the page gave up on (the 5-second timeout) from reaching the server after the removal, and the first version only documented that. Now a removal is remembered on the server (`device_token_removals`, one row per user type, person and token, migration `2026-11-02-issue-022-device-token-removals.sql` with a rollback), and `register` refuses a registration whose access token was issued at or before that removal. `iat` (the token's issue time, in whole seconds) is read from the verified token, never from the body, so a registration cannot claim to be newer than its sign-in. A later sign-in has a newer token and registers normally; another person, or the same person in the other area, is not affected. The refused registration gets `409` and the page treats it like any failed registration (silent, no refresh, no sign-out). Registering and removing for one person take the same advisory lock, so they are handled one after the other whatever order they arrive in, and a removal of a phone that is not registered yet (or is owned by someone else now) is still remembered. Rows older than a day are deleted by the next removal (an access token lasts minutes). A token with no `iat` cannot be compared and is accepted as before (the server always issues one). Remaining limits: whole-second resolution means a person who signs out and signs in again within the same second would have that first registration refused (it is retried at the next start); and a phone whose old owner never managed to send the removal (an already-expired session) is still handed to the next person by their own registration, as documented below. This covers the normal logout and the other in-app sign-out paths. When the session is already dead (an expired refresh token), the removal cannot be authorised and the phone stays registered to that person until the same phone is used to sign in (the server then moves it to the new person) or Expo reports the token invalid. Lock-screen text is generic and a tap checks sign-in, so the exposure is small.
- **Tap routing (`PushTapRouter`).** On the shell's data-free nudge (and once at start, for a tap that opened the app from closed) the page collects the screen name through the bridge and maps it per area: driver `availability`, `deliveries`, `agreement`; admin `access-codes`. A name not listed for the signed-in area, or any URL, is ignored. If nobody is signed in yet the tap waits up to 10 minutes for a sign-in. If someone is signed in whose area cannot open it, it is dropped and does not follow a later sign-in. The route guards (agreement, role, sign-in) and the server still decide what is shown.

**Android first run (review fix).** Android's notification module reports `denied` with `canAskAgain: true` before the first grant; it has no "not asked yet" state like iOS. `PushSetup` only offered the explanation for `undetermined`, so Android never saw it. It now asks for `undetermined` and for `denied` while `canAskAgain` is true, and leaves a refusal the system will not repeat alone.

**Risks and follow-ups.** There is no "notifications are off, open settings" screen yet (the shell action `push.openSettings` exists); a person who refused must find the phone's settings themselves. Account-level on/off switches per event are left for later. The design's note on logout cleanup is met on the normal path only, as described above.
