**Why.** Admins need to tell Local drivers from Desi drivers, one at a time or many at once.

**What changed.**
- **Database:** `drivers.driver_type`, a nullable text column that only accepts `LOCAL` or `DESI` (a CHECK constraint). **Existing drivers are not classified.** Nothing in the data says which kind a driver is, and a wrong guess is worse than a blank, so all of them start as NULL and show as "Not set" until an admin picks. Adding a nullable column with no default rewrites no rows.
- **API:** `PATCH /admin/drivers/type` with `{ "driverIds": [..], "driverType": "LOCAL" | "DESI" }`. Any admin, but only for drivers in their own cities (a driver with no city: super admin only). It validates the body (1 to 500 whole-number IDs, repeated IDs count once, an exact type) and answers 400 otherwise. In one transaction it locks the rows, answers 404 if any ID does not exist and 403 if any driver is outside the admin's cities (nothing is changed in either case), then updates only the drivers whose type is different, so drivers already of that type are not rewritten. The answer says how many were updated and how many were already that type. A database error rolls everything back.
- **Reads:** the five queries that return a driver row for the Drivers table (list for super admin, list for an admin, after create, after enable/disable, after edit) now include `driver_type`, so toggling or editing a driver does not make the type disappear from the row.
- **Screen:** a "Driver Type" column (Local, Desi or Not set); a checkbox on every row and one in the header (select all on this page, half-selected when only some are); a **Change (n)** button that is hidden until someone is selected; a modal titled "Change Driver Type" with the number selected, the choices "Change to Local" and "Change to Desi", Cancel and Confirm (Confirm stays disabled until a choice is made). Confirm sends one request, shows "Updating...", blocks a second submit and cannot be closed while it runs; on success the rows change at once, the selection clears, the modal closes and a message says how many changed; on a refusal the modal and selection stay and the server's message is shown. If everyone selected is on the page and already has the chosen type, nothing is sent.
- **Selection rules:** it stays when moving between pages (the count includes drivers on other pages) and starts again when the search or the city filter changes, so a driver you can no longer see is never changed by accident.
- **Add and Edit driver form:** a "Driver Type" dropdown (Not set, Local, Desi). It is optional. On Add, nothing chosen creates the driver as "Not set". On Edit it shows the driver's current type; leaving it alone keeps that type (the dropdown only reads "Keep current type" when one is set, so it cannot be used to clear it by accident). The create and update endpoints accept an optional `driverType`: left out or empty means no choice, anything but `LOCAL` or `DESI` is a 400 before anything else is checked. The update uses `COALESCE`, so an absent type never changes the stored one.
- The new request has its own `changingType` flag, so the table never flips to its loading skeleton while a change runs.

- **Database:** additive. Run `Backend/migrations/2026-11-06-issue-232-driver-type.sql` (back up first, on a copy first; safe to run twice). Rollback: `...driver-type.rollback.sql` (deletes the choices admins made). Applied to the local `nasa_local` after a backup of the `drivers` table: 732 drivers, 0 classified.
- **Config and dependencies:** None. **Money impact:** None (no pay, rate or Excel logic touched).

**Risks and follow-ups.**
- The type is optional on the Add form on purpose, so existing flows and API callers keep working. Making it required for new drivers is a one-line change in the form's validation plus the server check; say if you want it.
- The type is not used anywhere else yet (pay, reports, Insights).
- Naming follows this module's existing habit: rows come back as `driver_type` (like `driver_code`) and request bodies use `driverType` (like `phoneNumber`).
