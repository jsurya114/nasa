The setup state is read again right after signing. No loop (tested with the real guard).
- **A driver with no type** sees a quiet "waiting for your admin" and is never asked to set up. Desi sees nothing.
- **The setup page:** states Not started / Setting up / In progress / Checking / Ready / Needs attention / Unavailable, in plain words, English and Spanish. Everything goes through the translation helper with Spanish added; the server's refusal of a held driver (journey, availability) is returned in the driver's language too (`onboarding.required`).

**How Everee's screens open (web).** In an iframe, as Everee documents, with a **private MessageChannel created for each load**. The port is sent only to the link's own origin (never `*`). An event is read only from that port, only if it is a plain object with a known `eventType` and this session's handler name; anything else is ignored. A completion or close event **never marks anything complete**: it makes the page ask the server (which asks Everee), a few times over about 5 seconds, then says "still checking" and offers "Check again". Error events, a link that never connects (10 s) and an expired link each close the window with a clear message and a way to resume with a fresh link. The link must be https on an Everee host and match its origin or no frame is rendered; it lives in one component's props only and is dropped when the window closes (never in Redux, storage, the URL or a log; tested). No `sandbox` attribute is set because Everee documents none and its screens need scripts, forms and their own storage; the frame gets no device permissions (`allow=""`).

**How they open in the phone app.** The NASA WebView blocks third-party frames, so a frame cannot be used. The page asks the shell for one new bridge action, `everee.open`, with **only the link** (accepted only as https on `everee.com`). The shell opens a **separate WebView in a modal**: no bridge, no nonce, no session token, no injected script, incognito, only Everee addresses may load (`shouldLoad`), one window at a time, Back and a Close button close it. The window ends on Everee's own `DISMISS`/`WORKER_ONBOARDING_COMPLETE` message (handler name `ReactNativeWebView`, which the server uses for platform `native`) or when the person closes it; the page learns only "finished / closed / error" and then asks the server, as above. The privileged bridge is not widened to Everee content; the main WebView's protections are unchanged and tested. An app too old to know the action says "update the app".

## Review round 1 (Jasil, two P1 on this PR)

1. **A healthy Everee screen was closed after 10 seconds.** The session check made a new object on every render and the connection timers depended on it, so hiding the "Opening Everee…" line when the screen registered re-ran the effect, reset the "registered" flag and started a new 10 second timer. (Confirmed by Jasil in a component test and in Chrome with a real MessageChannel.) Now the session is checked once per session (`useMemo`), the timers are armed once for that session, and they are **cancelled for good the moment the screen registers**, so nothing later (the connection wait or the link's expiry) can close a working screen. An unregistered screen still times out.
2. **No way to ask again after an unfinished check.** After three unfinished checks the page said "Press Check again" but the button only existed for the "verifying" state, so a driver in "in progress" only had Continue, which opens another Everee window. Now an unfinished or failed check (including a refresh outage) always leaves a **Check again** that asks the server, next to Continue and without opening anything; it goes away once the server says complete. If Everee refuses a new window because the setup is already complete, the page now reads the status from the server instead of showing an error.

Four regression tests: a registered screen stays open past the connection wait, the link's expiry and unrelated re-renders; a completion that becomes visible only after the first checks is found with Check again and no window opened and no reload; a refresh outage then recovery; and "already complete" turning into a status check. All four fail on the previous code. PR #243 and #244's reviewed fixes are merged into this branch.

## CI follow-up for review round 1

The "connected screen stays open" test passed on a fast machine and failed in CI ("did not connect" after 15 s). The component is now stricter and the test no longer depends on a fake clock: **registration belongs to the session** (`registeredFor`), so no effect that runs late, no re-run and no re-render can make a registered session look unregistered or re-arm its timers; and the connection wait can be shortened for tests (`connectTimeoutMs`, default 10 s). The long fake-clock integration test was replaced by `EvereeEmbed.test.jsx`, which uses real timers and short waits: a registered screen stays open past the wait, past the link's expiry and through re-renders; a screen that never registers closes as "no connection"; a link that runs out first closes as "expired"; events and the port's target origin are checked. #243 was also merged into `develop` meanwhile, so this branch now has `develop` merged in.
