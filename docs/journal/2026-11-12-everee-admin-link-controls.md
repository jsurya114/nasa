**What and why.** A driver can end up registered twice (an old disabled record that is already linked to her Everee worker, and a new active record). The new record then sits at "Needs review" and the driver is locked out, and an admin had no way to fix it except calling the backend directly. Agreed with Jasil on Slack (12 Nov): keep the active record, keep the old disabled one for history, reuse the existing Everee worker, and add admin controls.

1. **Look up, Link and Unlink on Driver payment setup** (super admin only; the server checks the role and the admin's cities again). Every needs-review card has "Look up in Everee". The result shows the candidate worker's name and masked email and phone, whether it matched on email, phone or both, and a conflict if one detail matches and the other differs. The rules are unchanged: a worker is linked only from one exact email or phone match, never by name.
2. **A disabled record's link is now visible.** When ONE clean match is still linked to another driver record, Look up returns that record (name, driver code, enabled or disabled, city) and whether it has unsettled Everee payments. "Remove link from that record" needs a reason of at least 3 characters, works across cities for a super admin, then looks up again so the admin sees the clean match before pressing "Link this worker". The old link row is kept as history (who, when, why).
3. **Unlink now refuses while the driver has unsettled Everee payments** (sent and not confirmed, not sent, or a returned deposit: the same rule the readiness page uses) unless the request says `acknowledgeOutstanding: true`. The screen asks for a tick box first. This is the "check outstanding payments before moving the link" step.
4. **Adding a driver with a name that already exists names the record to review** (driver code and enabled or disabled) instead of only "already exists". A name that differs only by punctuation or spacing ("Sam Lee" and "Sam Lee..") is a question: the server answers 409 `similar_driver` with the matching records, and the Add Driver screen asks "This is a different person: create anyway" or "Go back". Only records in cities the admin manages are named. The old exact-name rule (#177) is unchanged.

**Not changed:** the name rule, the exact-match linking rules, what makes a driver Onboarded (only a link to a worker that Everee reports complete), and anything about pay amounts.

**Database.** None.

**Config and dependencies.** None.

**Money impact.** None. No pay, rate, deduction or payment logic changes. Moving a link changes which NASA driver record the Everee worker belongs to; old work and pay records stay on their original records. The unsettled-payments check only makes an Unlink harder, never easier.

The existing Everee, readiness, onboarding and contact tests still pass (44 passed, 0 failed in those files).

New cases cover the whole move (masked candidate, holder named, reason required, Unlink sent for the other record in its own city, Look up again, Link), the unsettled-payments tick box, the no-match, conflict and incomplete-driver messages, a server refusal, and the similar-name question.

**Not tested.** Real Everee or the production database; a click-through in a browser; a phone. The "unsettled payments" test replaces the answer to that one query (building a pay run and payment item for it needs a long chain of records); the same SQL runs unchanged in the Look up test and on the readiness page. That an admin without access to a city is not told about a record in it is written into the code but not covered by a test.

**Risks and follow-ups.**
- Look up on the new record finds the worker only if the new record's email or phone equals the worker's. If the two NASA records have different contact details, the lookup says no match; confirm the real details with the driver and correct them in Users first (a driver whose own email or phone change is waiting for confirmation, from #278, is also blocked until a super admin confirms it).
- Do the production move in this order: check the exact review reason on the card, check the worker in the production Everee company and the old record's payments, Look up, remove the link from the old record with a reason that names the move, Look up again, Link, ask the driver to reopen the app.
- The near-duplicate check ignores everything except letters and digits and uses the database's idea of a letter, so with a plain "C" database an accented letter can be dropped on both sides. It is a warning only, never a block.
- An admin can still press "create anyway" for a genuinely different person with a near-identical name.

## Review round 1 (Jasil on c60df6d)

1. **Ambiguous, truncated and conflicting matches stay read-only.** Look up used to replace any result with "blocked" whenever a candidate was linked elsewhere, so the screen could offer to remove a link on a guess. Now the original result is kept (`ambiguous`, which also covers a truncated search, or `conflict`) and the holder is only shown. "Blocked by another driver", and the link to remove, are returned only for a single clean match (`match`). The screen offers removal only then (it also checks that there is one candidate and a link ID). A test covers a conflicting, an ambiguous and a truncated linked candidate: result unchanged, no link ID, cannot be linked, old record still linked. The older test that expected "blocked" for a worker whose phone matched with another email now expects `conflict`.
2. **Unlink removes the exact link that was reviewed.** Look up returns the holder's link row ID (`linkedDriver.linkId`). Unlink now requires it (400 without it) and removes only that row, checked under the driver's lock. If the driver's active link is a different row by then, the server answers 409 "link changed since you looked it up, look up again" and removes nothing; if there is no active link it is still 404. The screen drops the old result as soon as the unlink succeeds or is refused, so a failed follow-up look-up leaves no remove button. Existing tests that unlink (`evereeWorkers`, `evereeDriverLock`, `evereeWorkGate`) now pass the link ID.

**Tested in this round.** Database tests 56 passed, 0 failed (the Everee link, similar-name, readiness, onboarding, gate and contact files); backend without the database 318 passed; frontend 601 passed, build and lint pass. **Not run:** `evereeDriverLock` and `evereeWorkGate` are commit-mode tests that need a throw-away database whose name contains "test"; I changed one line in each (reading the link ID) and checked they parse, but they did not run.

## Review round 2 (Jasil on f16e49f)

1. **Unlink and payment reservation are serialized.** The unsettled-payments check used to run before the unlink transaction, so a payment batch that was still reserving the driver (its item not committed yet) could be missed, and the unlink then ran after the batch committed, without the acknowledgement. Now the check and the unlink are one transaction under the driver's lock, and it first takes the driver row in `FOR NO KEY UPDATE` mode. A payment batch holds that row in `FOR SHARE` mode while it reserves, so the unlink waits for the batch to commit, then sees its payment. `NO KEY UPDATE` was chosen so inserts that only reference the driver are not held up. A batch that starts after the unlink has taken the row waits for the unlink instead.
2. **The reason and the confirmation tick are cleared whenever a result changes.** Starting a look-up, showing a result, and dropping one (after a successful or refused unlink, or after Link) all reset both, so a later look-up with a different holder and unsettled payments never inherits what was typed or ticked.

**Tested.** `evereeUnlinkLocking` uses two real connections: a batch holds the driver row, the unlink waits (pending), the batch commits, and the unlink refuses without the acknowledgement; with the acknowledgement it unlinks; with no batch it does not wait. The payment item itself is not built (it needs a pay run, a statement and a batch), so the answer of the "unsettled payments" query is stood in for, and it becomes "unsettled" only once the batch has committed. The test fails when the lock line is removed. That includes the two suites I had changed in the first review round and could not run then. Frontend: 602 passed, build and lint pass; the new stale-state test fails when the reset is removed. Backend without the database: 318 passed.
