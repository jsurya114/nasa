**This is the step that sends money**, so it is guarded in layers. Nothing is sent unless `EVEREE_PAYMENTS_ENABLED` is exactly `true` (off by default), Everee is set up for the sandbox (a production token also needs `EVEREE_ENVIRONMENT=production` **and** `EVEREE_PRODUCTION_PAYMENTS_APPROVED=true`, which stays unset until Jasil approves in chat), the person confirming is a super admin who did not finalize the run, and the preview they saw is unchanged.

**The order, per confirmed click** (`POST /admin/payroll/runs/:runId/everee-batches`, body `requestId` and `previewHash`):
1. **One short transaction.** Lock the run, then the city (the same order as `recordRunPayment` in #202, so the two cannot race), repeat the preview and compare its hash (a change is a 409 that carries the new preview), check the included earnings did not change, then **reserve** every statement (`payout_status = submitted`) and write the batch and one item per statement. From then on manual recording is blocked for them and so is any other batch.
2. **Per driver, outside any transaction.** The attempt row is written first, then the payable is sent with a stable external ID (`nasa-stmt-<statement id>`, the idempotency key), then the answer is written. A 4xx or an exhausted 429 means Everee did not take it: `failed` (safe to retry). A timeout, a lost connection, a 5xx or an answer for another payable means unknown: `unconfirmed`, never `failed`. A 429 is waited out (Everee's `RateLimit-Reset`, else a growing wait with jitter) and repeated up to 3 times; requests are spaced about 120 ms apart (the limit is 100 per 5 seconds).
3. **One payout request** (`/payables/payment-request`) limited to exactly this batch's accepted payables. If Everee takes fewer than asked, each payable it left is read back: a status that means "already in payment" is recorded (a lost reply to an earlier request); a blocked status (`ERROR`, unpayable worker, deleted) makes it `unconfirmed` with a message, so it cannot be marked paid by hand or retried blindly until someone has checked Everee.
- The same request ID returns the same batch and sends nothing. The same ID for another run, admin or preview is a 409.
- **"Paid" is never set here.** Hosted payroll: an admin approves the payments in the Everee portal, and "paid" means the money landed, which the next part reads back (webhooks and the Payment Data API). The earning rows (`dashboard_data`, `payment_dashboard`) are not touched.
- `POST .../everee-batches/:batchId/retry` sends again **only** items that failed (the same external ID) and asks for payout of payables Everee has accepted but not yet been asked about. It never touches submitted, unconfirmed or paid items. A statement marked paid by hand in the meantime, a worker who is no longer ready, or changed earnings stop that item. Same permission as confirming.
- `GET .../everee-batches/:batchId` and `GET .../runs/:runId/everee-batches` give the per-driver results. No Everee worker ID is shown.
- **City settings** (`GET /everee/city-settings?cityId=`, `PUT /everee/city-settings/:cityId`, super admin): the time zone (the earning date is the run's last day at noon in it; the sandbox default is America/Chicago) and the Everee work location (sent on every payable). A live (production) batch is blocked for a city without both, as Jasil asked.
- The preview now also blocks a statement that is already in an Everee batch (`in_everee_batch`).

**Database** (`2026-11-04-issue-031-everee-payments.sql`, additive; the rollback refuses to run if any batch exists; back up and run on a copy first). Five tables: `everee_city_settings`, `everee_payment_batches`, `everee_payment_items` (**one item per pay statement, ever**, unique; unique external ID), `everee_payment_attempts` (written before each request, finished once) and `everee_payout_requests`. A trigger refuses deletes everywhere, makes batches immutable, keeps an item's identity and amount fixed (only its status and Everee's answers change) and lets an attempt or payout request be finished once. Applied to the local copy only. (The manual payment records migration from #202 was applied to the local copy too.)

- **Dependencies:** none. **Config:** `EVEREE_PRODUCTION_PAYMENTS_APPROVED` added to `.env.example` (the switch `EVEREE_PAYMENTS_ENABLED` was added in part 3).
- **Money impact:** this code can send payables to Everee and ask for payout, but only with the switch on, and the sandbox moves no real money. No pay-run amount, statement, deduction or earning row is changed. A statement's frozen net is sent as it is. The change to `paymentRecords.js` only exports two helpers (the manual flow is unchanged; Jasil's 8 payment tests pass).

**Review hardening (automated security review of the first push).** The retry checked that the driver's *current* Everee worker was ready but sent to the worker saved on the payment, so a driver unlinked and linked to a different worker in between could have been paid at the old one on the strength of the new one's status. The retry now sends only when the current link is the same worker (both IDs) the payment was made for; otherwise the item stays `failed` with an explanation. The retry also enforces the batch-level rules of confirming that can change after a batch: the run must still be finalized, and a live batch needs its city settings. Removing either fix fails the new steps (checked).

**Tested.** Pure (5): the noon calculation across both clock changes, the payable body (no personal data), the failure classes. Database with a fake Everee, rolled back (19 steps): every refusal writes nothing; a confirmed batch sends the right payables and one payout request and never "paid"; replay; manual recording blocked while submitted and a second batch refused; a statement paid by hand is never sent; partial failure; retry only of what failed with the same ID; retry skips a statement paid by hand and a worker who left; rate limits; a failed payout request repeated alone; a wrong answer and an empty payout request; a payable blocked at Everee; an unreadable status; changed earnings; city settings and the live guards; the database guards. Breaking the hash check makes 5 steps fail, calling a timeout "failed" makes 3 fail, and letting retry take unconfirmed items (both layers) makes 6 fail (checked). Backend suite: 371 pass, 4 fail; the same 4 claims-store tests fail on `develop` without this change.

**Sandbox evidence** (real Everee sandbox, a throwaway database, made-up drivers and fake amounts of $1, $2 and $3; counts and statuses only):
- 3 sandbox test workers reused (not duplicated), all ready. Preview: 3 eligible, $6.00, can submit. The person who finalized tried to confirm: refused (403).
- Confirmed by the other super admin: **3 payables accepted by Everee (HTTP 201)**, 3 attempts recorded as accepted. The payout request returned HTTP 200 and took 0 of 3 ("nothing to process"). Everee reports all 3 payables as **`ERROR`**, so the batch ended with 3 `unconfirmed` and an explanation; **nothing was paid and nothing is marked paid**. The same confirmation again sent nothing (attempts stayed 3).
- Race 1, two admins confirming the same preview at the same moment on committed data: exactly one batch with 3 items; the other got 409. Race 2, Everee against recording by hand: Everee ok, the manual recording refused (409), 0 manual receipts.
- **Open finding: why Everee says ERROR.** It does so for every payable we sent, whatever the earning date (past, now, future) and with or without a work location (the sandbox company had none; one was created and made no difference). The workers are onboarded with a bank account and tax ID check `NEEDS_VERIFICATION`. The reason text is not in the API; it is probably in the Everee portal (Payments, or View webhook events). The first real "money landed" evidence needs this resolved in the sandbox (a company or worker setting). Until then the safe behavior above is what happens.
- Other things the sandbox taught: an earning date before the worker's start date is refused (400, with a clear message); a work location address must geocode (a made-up street fails, a real public address works); the payable status is only visible by reading the payable.

**Not tested.** A payment that reaches "paid" (blocked by the open finding); a real webhook for a payment event (part 5); no screen (the dashboard Pay button is the last part). How often to poll for status is decided in part 5.
